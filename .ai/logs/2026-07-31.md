action: fix — algolia/tag-present-in-v5.js's AddUnique array operation on docusaurus_tag
  wasn't persisting; switched to a plain full-array overwrite
context: user manually verified the dev index after a real crawl+prune+tag run, using the
  Algolia dashboard's facet browser. For component:eventcalendar, docusaurus_tag facet
  values were docs-default-6.1.0 (28,539) and docs-default-5.35.0 (1,822) — summing exactly
  to the component's total (30,361), proving zero overlap: no record had both tag values,
  even though tag-present-in-v5.js's own log reported "Tagged 56112 anchored records (36746
  presentInV5:true, tag added)". Separately, component:popup showed zero
  docs-default-5.35.0 records at all — consistent with the same root cause (popup has no
  v5-only content of its own to fall back on, unlike eventcalendar, so the missing tag
  addition is fully visible there instead of partially masked). User then confirmed
  directly: presentInV5 (a plain field in the same partialUpdateObject body) DID show up
  correctly with both true/false values, but docusaurus_tag (written via an AddUnique
  operation object) did not change at all — isolating the bug to AddUnique specifically,
  ruling out a general async-propagation delay (since a plain field write in the same
  request succeeded immediately).
outcome: |
  Root cause not fully isolated (no direct Algolia API access available to test AddUnique's
  exact behavior in isolation), but rather than keep debugging an operation whose precise
  semantics couldn't be verified, replaced it with a write that doesn't depend on any
  special operation at all: algolia/tag-present-in-v5.js now sets
  `body.docusaurus_tag = [`docs-default-${currentVersion}`, 'docs-default-5.35.0']`
  directly — a plain full-array overwrite, the same kind of write that already worked
  correctly for presentInV5. Safe because every record processed here was already browsed
  via a `docusaurus_tag:"docs-default-<currentVersion>"` filter, so its value going in is
  known to be exactly that single tag; overwriting with an explicit 2-element array
  including that same value back is equivalent to "adding" the legacy tag, without relying
  on AddUnique's append-if-array/convert-if-scalar behavior actually working as documented.
  Updated algolia-search.md's description of tag-present-in-v5.js to match.
  Not yet re-run against the dev index — next step is to re-run the crawl workflow (or just
  the Tag step) and re-check the same eventcalendar/popup facet breakdowns for overlap.
learnings: |
  A batch write returning HTTP success only proves the request was syntactically accepted,
  not that every operation inside it produced the intended effect — confirmed concretely
  here: AddUnique's write was silently accepted (no error thrown) but never applied. When a
  script's own "success" log and the live data disagree, trust the live data and stop
  relying on the operation's documented behavior matching reality; switching to a
  dependency-free plain overwrite removed the need to get that operation's semantics right
  at all. Also a good general technique from this exchange: isolating "does field A change
  but not field B in the same request" is a precise way to rule out propagation delay
  (which would affect both) versus an operation-specific bug (which affects only one).

action: fix — "no anchor = guide page, always keep" was wrong; guide headings have real
  anchors too, so prune-v5-duplicates.js was deleting v5.35.0's own hand-written content
context: user asked why presentInV5 was false for accessibility.md's "1-perceivable"
  heading on both popup and eventcalendar. Investigated rather than assuming: Docusaurus
  assigns a real, non-empty anchor id to EVERY heading, not just auto-generated API ones —
  "1-perceivable" is a genuine anchor, just not one of the opt-/event-/method-/type-/
  renderer-/slot-/template-/view-/localization- prefixes generate-v5-anchor-sets.js tracks.
  presentInV5 defaulting to false for it is technically correct (never classified), but
  exposed a much worse bug: prune-v5-duplicates.js's guide-page protection was
  `if (!hit.anchor) return`, which only protects records with NO anchor at all — it never
  applied to "1-perceivable" (a real, truthy string), so that heading (and any other
  hand-written guide-page heading with a real anchor, on ANY page, not just accessibility.md)
  was being deleted as an unverified "duplicate" it was never actually confirmed to be.
outcome: |
  Added `isTrackedAnchor()` to algolia/lib.js — tests whether an anchor matches the same
  prefix list generate-v5-anchor-sets.js extracts (exported as TRACKED_ANCHOR_PREFIXES, and
  generate-v5-anchor-sets.js now builds its own regex from that same exported list instead
  of a separately hardcoded copy, so the two can't drift apart again). Verified:
  isTrackedAnchor('opt-actionableEvents') -> true, isTrackedAnchor('1-perceivable') -> false,
  isTrackedAnchor(null) -> false.
  prune-v5-duplicates.js: replaced `if (!hit.anchor) return` with
  `if (!isTrackedAnchor(hit.anchor)) return` — now correctly protects ALL non-API-reference
  content (guide headings with real anchors, and records with no anchor at all), not just
  the anchor-less subset.
  tag-present-in-v5.js: same replacement, for consistency and to skip pointless writes on
  guide-page records that were always going to classify as presentInV5:false anyway (this
  one wasn't destructive like prune's version, just noisy).
  Regenerated v5-anchors.json/v5-only-anchors.json after the generate-v5-anchor-sets.js
  refactor — confirmed byte-for-byte identical (git diff empty), proving the refactor didn't
  change extraction behavior, only removed the duplicated prefix list.
  Not yet re-run against the dev index — next crawl+prune+tag run should show MORE
  surviving v5.35.0 records than before (previously-deleted guide headings restored), not
  fewer.
learnings: |
  "Does this record have field X" is a weaker and different test than "is this record of
  category Y" — I used the former (hit.anchor truthiness) as a proxy for the latter
  (auto-generated API content vs. hand-written guide content) without checking whether
  every record in the "guide content" category actually lacks that field. It didn't:
  Docusaurus's own heading-id behavior meant nearly all guide headings still have a real
  anchor, just an untracked one. When a proxy condition and the actual category it's meant
  to represent aren't provably equivalent, check a real example from the category the proxy
  is supposed to protect — not just examples from the category it's supposed to affect.

  `<th><p>Compatibility</p><label><input type="checkbox">
  <p>Show only applicable items</p></label></th>` — the checkbox's caption `<p>` directly
  follows an `<input>` sibling. search-config.json's `text` selector's
  `:not(h3):not(.badge--secondary) + p` rule (added 2026-07-24 to skip a type-signature
  paragraph after API headings) matches ANY `<p>` following a non-h3/non-badge sibling
  anywhere in the article — including this checkbox caption, which is UI chrome, not
  content. Confirmed unrelated to js_render, unrelated to the v5.35.0/presentInV5 work
  (both compared results were plain v6 queries), and present on every framework's
  accessibility page identically (shared table markup), so this would also affect prod once
  prod is eventually re-crawled with any config.

  search-config-dev.json — `article :not(h3):not(.badge--secondary):not(input) + p, ...`.
  A plain CSS3 simple-type exclusion (no ancestor/descendant combinator needed, so no
  cssselect-compatibility risk), verified logically against the fetched markup: the
  checkbox caption's immediately-preceding sibling is exactly `<input>`, so this excludes
  it, while no legitimate description paragraph anywhere follows a raw `<input>` sibling.
  Not yet re-crawled/verified live — needs a fresh crawl on both search-config files to
  confirm the checkbox caption no longer gets indexed.
learnings: |
  A selector written to fix one narrow case (skip the type-signature paragraph right after
  an h3) used a general "sibling + p" CSS pattern that silently applies everywhere in the
  document, not just the intended context — this is the second time this session a "+p"/
  sibling-adjacency selector has caught unintended content (the first was the badge-selector
  fix from 2026-07-24). Worth remembering: any selector rule meant to target one structural
  pattern (heading + description) should ideally be scoped as narrowly as the pattern it's
  actually meant to match, not left as a broad sibling-combinator rule that happens to work
  for the observed case.

timestamp: 2026-07-31T03:00:00Z
action: fix — SearchBar's transformItems was frozen via useRef, causing v6-page searches
  to rewrite result URLs to v5.35.0 once triggered once from a v5.35.0 page
context: user's manual testing (guides worked, then eventcalendar renderSchedulerEvent-type
  cases) found shared AND pure-v6-only options both linking to v5.35.0 pages even when
  searching from a v6 page. Confirmed via the network payload that the query itself was
  correctly v6-scoped (facetFilters right for the current page) — only the returned result
  URLs were wrong, isolating the bug to the client-side URL-rewrite step, not the query.
outcome: |
  Root cause: SearchBar/index.js's `transformItems` was defined as
  `useRef((items) => {... transformItemsForLocation(items, locationInfo) ...}).current` —
  useRef only uses its argument on the component's FIRST render; later renders' updated
  `locationInfo` never replace the frozen closure. This search widget lives in the
  persistent navbar and doesn't remount on client-side navigation, so once the first
  render happened to be on a v5.35.0 page, that stale `locationInfo` (with
  isLegacyV5Page permanently true) got baked in — every later search, from any page,
  including pure v6-only content never tagged presentInV5, kept getting its result URLs
  rewritten into /5.35.0/, regardless of the actual current page or the correctly-scoped
  query.
  Fix: removed the useRef wrapper — transformItems is now a plain function recomputed
  every render, always using the current-render's locationInfo. Cheap enough to not need
  memoizing (a items.map() call). Checked SearchPage/index.js for the same pattern: not
  affected — its isLegacyV5/URL-rewrite logic already runs fresh every render (algoliaHelper
  itself is recreated fresh per render, not memoized, and its result handler is registered
  directly on that fresh instance), and makeSearch is wrapped in Docusaurus's useEvent
  (which is specifically designed to always call the latest closure, unlike plain useRef).
  npm run typecheck still only shows the pre-existing unrelated HomepageFeatures errors.
learnings: |
  `useRef(fn).current` is a footgun for any callback that closes over a value which changes
  across renders but isn't itself in a dependency array forcing a remount — it silently
  freezes at first-render values with no warning, no error, just quietly-wrong behavior
  later. This exact pattern already existed in the file before this session's changes
  (wrapping the original, locationInfo-independent transformItems), so it wasn't a bug then
  — but became one the moment a per-navigation-changing value was added inside it. When
  reusing an existing useRef/useMemo/useCallback wrapper for new logic, check whether the
  new logic's dependencies actually match what justified the memoization in the first place.

action: feature — made the navbar version dropdown reflect v5.35.0 context on the search
  results page
context: user's manual testing found that after landing on the search results page
  ("See all results") from a v5.35.0 page, the navbar's version dropdown always showed the
  latest version instead of 5.35.0, even though the search itself was correctly scoped and
  linking to the right pages. Investigated: this is a separate, pre-existing UI component
  (src/theme/NavbarItem/DocsVersionDropdownNavbarItem.js, already custom-swizzled in this
  repo), unrelated to the Algolia indexing/tagging work — it determines the "active" version
  via Docusaurus's useActiveDocContext/useDocsVersionCandidates, both of which read the
  CURRENT ROUTE's doc metadata. /search isn't a doc route at all, so those hooks have
  nothing to read and default to latest.
outcome: |
  SearchPage/index.js already tracks this exact context via a `tag` URL param
  (getDefaultTags() in searchLink.ts, checked against LEGACY_V5_TAG) — reused that same
  signal in DocsVersionDropdownNavbarItem.js instead of inventing a new mechanism.
  When on `/search` (checked via `pathname.endsWith('/search')`, robust across baseUrl/
  environment since searchPagePath isn't customized anywhere in this repo) and the tag
  param indicates v5.35.0, the dropdown now shows "5.35.0" as its label and marks it active
  in the item list, instead of defaulting to latest.
  Caught and fixed a Rules-of-Hooks violation while writing this: an early draft called
  `useDocsVersionCandidates(docsPluginId)[0]` only via `??` short-circuit
  (`legacyV5Version ?? useDocsVersionCandidates(...)`), which would skip the hook call
  whenever legacyV5Version was set — hooks must be called unconditionally every render.
  Fixed by calling the hook first into its own variable, then applying `??` afterward.
  This file is .js/JSX, outside tsc's scope; validated by parsing it through
  @babel/preset-react directly (no syntax errors) since no eslint config exists in this repo
  to lint it with.
learnings: |
  When reusing a `??`/short-circuit pattern to combine a new conditional value with an
  existing hook call, check whether the hook call is on the side that can get skipped —
  `a ?? someHook()` silently violates Rules of Hooks the moment `a` is truthy on some
  renders and not others, with no compile-time warning in a plain .js file (no eslint
  configured here to catch it via eslint-plugin-react-hooks either).

  targeted text edit instead of parse-modify-restringify, even when the modification itself
  is trivial.
