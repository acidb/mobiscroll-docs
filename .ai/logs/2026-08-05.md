# Agent Log — 2026-08-05 — build — stray NUL bytes corrupting generated HTML

---
timestamp: 2026-08-05T00:00:00Z
action: investigation + fix — discovered a pre-existing, unrelated build-toolchain bug that
  silently derails Algolia's crawler on some pages, and added a post-build sweep to neutralize it
context: while verifying the Angular #template-* selector fix (see 2026-08-04's log), confirmed
  agendaEmptyTemplate produces zero indexed content for a different, deeper reason: docsearch-
  scraper's HTML parser (lxml.html.fromstring, per algolia/docsearch-scraper's own source —
  scraper/src/strategies/default_strategy.py, scraper/src/helpers.py) stops building the DOM
  entirely partway through some pages, well before the templates section.
outcome: |
  Root cause, established with byte-level evidence:
  - A stray NUL byte (\x00) gets embedded in generated HTML immediately before the zero-width
    space (U+200B, \xe2\x80\x8b) that Docusaurus puts inside every heading's hash-link anchor
    (<h3 ...><a ... translate="no">​</a></h3>). Confirmed via curl-fetched live production
    HTML, the user's own view-source screenshot, and a local `npx docusaurus build` — reproduces
    identically across all three, so it's a build-toolchain artifact, not a live-server/CDN issue
    and not Windows-specific (the corruption already exists on production, which isn't built on
    Windows).
  - Once lxml's parser hits that NUL byte, it silently stops adding new elements to the DOM for
    the rest of that page. Verified via bisection: deleting ONLY the corrupted heading's own
    block from an already-fetched page restores full parsing (16 -> 184 of 185 headings);
    deleting any other block does not.
  - The corruption's exact position is NOT tied to any specific heading's name, length, or CSS
    class (confirmed identical `class="anchor anchorTargetStickyNavbar_Vzrq"` /hash-link markup
    on both auto-generated API headings and hand-written guide headings — one guide heading,
    "Configuring the view" on the calendar page, was hit too). It IS tied to a fixed byte offset
    counted from the start of each page's <article> content: two builds of the identical
    eventcalendar/api page with different <head> content (683 bytes apart) landed the NUL byte
    at different absolute file offsets but the exact same offset relative to <article> (43264
    bytes in, both times) - pointing at a chunk/buffer-boundary artifact somewhere in Docusaurus's
    SSR/static-file-writing step, not yet isolated to an exact library or line.
  - Ruled out as the cause: this repo's own scripts/strip-jsx.js (only ever reads/writes
    .txt/.md files, never .html - confirmed via its own file-collection regex) and
    docusaurus-plugin-llms's `processingBatchSize` option (confirmed via its source,
    node_modules/docusaurus-plugin-llms/lib/generator.js - purely batches that plugin's own
    document loop when generating its own separate .md/.txt exports, which came back completely
    clean of NUL bytes for the same pages/headings that are corrupted in the real .html output).
  - Real-world impact is uneven and content-dependent, not a blanket "X% of the site is missing"
    figure: checked five Angular eventcalendar pages that all embed overlapping auto-generated
    content (api, calendar, scheduler, timeline, agenda) - scheduler/timeline/agenda came back
    completely clean (0 headings lost), while api (169 of 185 lost) and calendar (132 of 134
    lost) were both hit independently. Cross-referencing reachability across all five pages
    (Algolia indexes each URL's crawl independently, so content lost on one page can still
    surface via another page that documents the same anchor and isn't itself broken), only 21
    anchors - mostly calendar-view-specific options/types/templates with no clean page to fall
    back on - are unreachable from every one of the five pages checked. Severity will differ per
    component/page and would need the same check to characterize elsewhere.
  Fix: added scripts/strip-nul-bytes.js, wired into all four build variants in package.json
  (build, build-staging, build-dev, build-localdev) immediately after strip-jsx.js. Scans every
  generated build/**/*.html file and unconditionally strips any NUL byte found (a NUL byte has
  no legitimate place in valid HTML output, so this is safe regardless of root cause). Verified
  against the real build/ output: found and cleaned 25 files (39 NUL bytes total) across many
  components/frameworks/versions, not just eventcalendar - confirming the bug is general, not
  eventcalendar- or Angular-specific. Reran the script a second time afterward to confirm
  idempotency (0 files found the second time). Measured cost: 0.86s for the cleanup pass against
  a 1m31.9s full `docusaurus build` (~0.9% overhead) - negligible.
learnings: |
  A parser silently truncating its own output (no thrown error, no warning) is far more
  dangerous than one that fails loudly - this went unnoticed because every symptom (missing
  search content) looked like a config/selector problem, and only reproducing the actual crawler
  code path locally (not just reasoning about search-config.json) surfaced the real, unrelated
  root cause underneath it.
  When a bug's trigger point moves between two data points, check what's actually conserved
  (byte offset relative to a meaningful landmark) rather than concluding "it's random" - the
  683-byte experiment turned an apparently non-deterministic bug into a precisely reproducible
  one.
  Don't conflate "why does the corruption get inserted" with "why does the parser fail after
  encountering it" - these turned out to be two independent mechanisms in this investigation,
  and an earlier bisection test aimed at the first question actually only ever answered the
  second, which briefly looked like a contradiction before being untangled.
