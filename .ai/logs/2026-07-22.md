action: audited existing Algolia search setup (indexing vs. query-time behavior)
context: user asked for a full audit of how search currently works, ahead of migrating
  from manual Docker-based crawling to automatic crawling, and adding Connect + 5.35.0

outcome: |
  Traced the full pipeline: manual `algolia/docsearch-scraper` Docker runs (documented in
  algolia-search.md) populate an Algolia index from `search-config.json`/`search-config-dev.json`
  crawl rules; live search queries hit Algolia's API directly from the browser via
  `src/theme/SearchBar/index.js` (@docsearch/react) and `src/theme/SearchPage/index.js`
  (algoliasearch-helper), using credentials from each `docusaurus.config*.js`'s `algolia`
  block. Per-page scoping is custom (not Docusaurus's built-in contextualSearch) via
  `src/components/Search/util.ts`'s getLocationInfo/getCustomFacets, which only ever pushed
  a `framework` facet — a computed `docsBase` (docs vs connect) was dead code, never used.
  Confirmed Connect was never crawled (`start_urls` never included `/connect/...`) and
  5.35.0 was actively blocked (`stop_urls` regex blocked all numbered-version paths) —
  both entirely unindexed. Confirmed via `build/sitemap.xml` that Docusaurus's own sitemap
  generation already lists both 5.35.0 and Connect URLs correctly, so sitemap coverage was
  never the gap — only the crawl config's own start_urls/stop_urls rules were.
learnings: this repo's search does NOT use Docusaurus's built-in `contextualSearch`
  facet-filter mechanism for version/instance scoping, despite the official Docusaurus
  DocSearch integration guide recommending exactly that (docusaurus_tag/version facets
  auto-injected via meta tags). Worth remembering when reasoning about this repo's search
  behavior — the custom `util.ts` facet layer is the actual source of truth, not
  contextualSearch.

    indexed from dev that doesn't exist yet on prod → dead link/404 on click), not a
    domain redirect.
