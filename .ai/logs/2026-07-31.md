# Agent Log — 2026-07-31 — algolia — fix AddUnique tag write not persisting

---
timestamp: 2026-07-31T00:00:00Z
action: fix — algolia/tag-present-in-v5.js's AddUnique array operation on docusaurus_tag
  wasn't persisting; switched to a plain full-array overwrite
context: user manually verified the dev index after a real crawl+prune+tag run, using the
  Algolia dashboard's facet browser. For component:eventcalendar, docusaurus_tag facet
  values were docs-default-6.1.0 (28,539) and docs-default-5.35.0 (1,822) — summing exactly
  to the component's total (30,361), proving zero overlap: no record had both tag values,
  even though tag-present-in-v5.js's own log reported "Tagged 56112 anchored records (36746
  presentInV5:true, tag added)". Separately, component:popup showed zero
  docs-default-5.35.0 records at all — consistent with the same root cause (popup has no
  v5-only content of its own to fall back on, unlike eventcalendar, so the missing tag
  addition is fully visible there instead of partially masked). User then confirmed
  directly: presentInV5 (a plain field in the same partialUpdateObject body) DID show up
  correctly with both true/false values, but docusaurus_tag (written via an AddUnique
  operation object) did not change at all — isolating the bug to AddUnique specifically,
  ruling out a general async-propagation delay (since a plain field write in the same
  request succeeded immediately).
outcome: |
  Root cause not fully isolated (no direct Algolia API access available to test AddUnique's
  exact behavior in isolation), but rather than keep debugging an operation whose precise
  semantics couldn't be verified, replaced it with a write that doesn't depend on any
  special operation at all: algolia/tag-present-in-v5.js now sets
  `body.docusaurus_tag = [`docs-default-${currentVersion}`, 'docs-default-5.35.0']`
  directly — a plain full-array overwrite, the same kind of write that already worked
  correctly for presentInV5. Safe because every record processed here was already browsed
  via a `docusaurus_tag:"docs-default-<currentVersion>"` filter, so its value going in is
  known to be exactly that single tag; overwriting with an explicit 2-element array
  including that same value back is equivalent to "adding" the legacy tag, without relying
  on AddUnique's append-if-array/convert-if-scalar behavior actually working as documented.
  Updated algolia-search.md's description of tag-present-in-v5.js to match.
  Not yet re-run against the dev index — next step is to re-run the crawl workflow (or just
  the Tag step) and re-check the same eventcalendar/popup facet breakdowns for overlap.
learnings: |
  A batch write returning HTTP success only proves the request was syntactically accepted,
  not that every operation inside it produced the intended effect — confirmed concretely
  here: AddUnique's write was silently accepted (no error thrown) but never applied. When a
  script's own "success" log and the live data disagree, trust the live data and stop
  relying on the operation's documented behavior matching reality; switching to a
  dependency-free plain overwrite removed the need to get that operation's semantics right
  at all. Also a good general technique from this exchange: isolating "does field A change
  but not field B in the same request" is a precise way to rule out propagation delay
  (which would affect both) versus an operation-specific bug (which affects only one).
