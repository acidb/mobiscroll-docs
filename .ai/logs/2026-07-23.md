# Agent Log — 2026-07-23 — algolia — cut SearchPage query volume from 4 requests to 1 per search

---
timestamp: 2026-07-23T08:00:00Z
action: removed unnecessary disjunctive-facet-count side-queries from the full /search page
context: user inspected the browser network tab after the previous session's "See all N
  results" fix and noticed the /search page's request payload contained 4 entries per
  search (requests[0..3]), not 1, and asked what requests[1] ("facetFilters: [[framework:
  vue],[type:content]], facets: docusaurus_tag") was for
outcome: |
  Explained: algoliasearch-helper automatically issues one extra facet-count side-query
  per attribute listed in `disjunctiveFacets` (drops that one facet's own filter, keeps
  the others, asks only for that facet's value counts, hitsPerPage:0) — needed only if
  the UI displays per-value result counts somewhere. `SearchPage/index.js`'s
  FrameworkSelectDropdown is a static hardcoded list that never reads these counts, so
  all 3 side-queries (for `type`, `framework`, `docusaurus_tag` — the last one added by
  the prior session's "See all results" fix) were pure overhead, quadrupling search
  volume on that page for nothing.
  Fixed by removing `disjunctiveFacets` from the algoliaHelper config entirely and
  building `facetFilters` directly (nested-array OR syntax, same convention
  `src/components/Search/util.ts`'s getCustomFacets() already uses for the popup) via
  `algoliaHelper.setQueryParameter('facetFilters', ...)`, bypassing the
  addDisjunctiveFacetRefinement API path that requires the side-queries. Necessary
  companion change: had to also replace the `addDisjunctiveFacetRefinement(...)` calls in
  `makeSearch()`, since calling that API on a facet no longer declared disjunctive throws
  at runtime — this was caught before verification, not shipped broken.
  Verified live via a fresh dev server + Playwright network intercept, both the
  single-tag case (5.35.0 + framework) and the homepage's two-tag OR case: exactly 1
  request now, with the same facetFilters shape/scoping as before the change.
learnings: |
  Correcting the record from yesterday's (2026-07-22) log: the "See all N results"
  scoping fix (searchLink.ts's `tag` param + SearchPage.js applying docusaurus_tag) was
  implemented and verified on 2026-07-22 but its commit was never actually made that day
  — it sat uncommitted alongside today's query-volume fix until the user asked for a
  commit message covering both together. Recorded here so the commit history and these
  logs stay consistent with what actually happened, since the 2026-07-22 log entry
  describes work that wasn't committed until 2026-07-23.

timestamp: 2026-07-23T09:00:00Z
action: made the "current UI version" facet value derive from Docusaurus's own version
  metadata instead of a hardcoded string, per an approved plan
context: user was concerned `util.ts`'s hardcoded `CURRENT_VERSION = "6.1.0"` would need
  manual edits on every future v6 release, and asked whether the docusaurus_tag itself
  could instead be renamed to a stable alias (like Connect's `docs-connect-current`),
  restating the actual goal as "when a new version appears we do not have to rewrite the
  crawl script and the queries every time"
outcome: |
  Two research agents investigated first (plan mode): (1) renaming the emitted
  `docusearch:docusaurus_tag` value is not officially/safely possible — it's computed by
  Docusaurus's own getDocsVersionSearchTag() and rendered by DocVersionRoot/SearchMetadata,
  neither of which is a listed swizzle-safe component (would need `--danger`, and even
  then risks duplicate meta tags); (2) confirmed the crawl config never hardcodes a
  version-string value (only the `docusaurus_tag` attribute NAME) and current-version
  start_urls have no version segment at all, so the crawl script does NOT need to change
  on a version bump today — only util.ts's CURRENT_VERSION did; (3) full repo-wide grep
  found the only unavoidable version-bump edits are docusaurus.config.*.js's 3 version
  keys (×4 files), versions.json, and version-map.json — nothing else.
  Given renaming would add unofficial-internals risk without even removing those
  unavoidable edits, implemented the lower-risk fix instead: added useCurrentVersion() in
  util.ts (wraps useLatestVersion('default') from @docusaurus/plugin-content-docs/client),
  removed the hardcoded constant, and threaded currentVersion through
  getLocationInfo()/getDocusaurusTag() from the two call sites that need it
  (SearchBar/index.js, searchLink.ts). The 5.35.0 detection stays hardcoded intentionally
  (v5 is frozen at that version per the user's stated plan).
  Verified live: caught a real, previously-unnoticed bug in the process —
  docusaurus.config.localhost.js names its version literally 'current' (not '6.1.0'), so
  local dev testing had been silently sending the wrong tag the whole time; after the fix
  it correctly sends `docusaurus_tag:docs-default-current` there, while an equivalent
  environment configured with a real version number would correctly get that number
  instead — confirming the value is now genuinely derived per-environment, not hardcoded.
learnings: this closes out the "future consideration" logged (but explicitly deferred) in
  .ai/logs/2026-07-22.md's fourth entry — the deferred approach turned out to be exactly
  the right one once the rename alternative was ruled out by research. Also worth
  remembering: the user explicitly rejected centralizing docusaurus.config.*.js's
  repeated version keys into one shared file, since different environments intentionally
  need to run different "current" versions (e.g. testing 6.8.0 on dev before it's on
  prod) — a shared config would break that.

action: hid the framework dropdown on /search when the search scope is Connect-only
context: user noticed the static framework `<select>` (Angular/React/Javascript/jQuery/
  Vue) still rendered on the dedicated /search page even when reached via "See all
  results" from a Connect page, where framework has no meaning at all
outcome: |
  In `src/theme/SearchPage/index.js`: computed `isConnectOnly = tags.length === 1 &&
  tags[0] === 'docs-connect-current'` from the already-available `getDefaultTags()` —
  specifically the *single*-tag case, not "tags includes Connect," since the homepage's
  scope carries Connect paired with a current-version tag (mixed results) where the

  `{!isConnectOnly && (...)}` and flipped the query-input column's className from a
  hardcoded `col--9` to `col--9`/`col--12` based on `isConnectOnly`, so the input fills
  the row when the dropdown is absent. No facet/query logic changes needed — `framework`
  state already defaults to empty on a Connect-originated search.
  Verified via direct /search?...&tag=... navigation (same technique as prior fixes) at
  three scopes: Connect-only (dropdown absent, input full-width), homepage's mixed
  Connect+current-version (dropdown present, unaffected), and a framework page (dropdown
  present, unaffected).

  in this same fix)

timestamp: 2026-07-23T10:30:00Z
action: fixed the Connect-only search input not actually expanding to full width on
  narrow/tablet screens, despite the previous entry's col--12 change
context: user asked to check why the input wasn't filling the row at narrow widths even
  after the dropdown-hiding fix above
outcome: |
  Root cause: `src/theme/SearchPage/styles.module.css`'s `@media (max-width: 996px)` rule
  hardcodes `.searchQueryColumn { max-width: 60% !important; }`, written assuming the
  framework dropdown always occupies the other 40% — this `!important` override wins over
  the Infima `col--12` grid class at any viewport ≤996px, so between ~577-996px the input
  stayed capped at 60% with an empty gap where the dropdown used to be (confirmed via
  Playwright: at 800px viewport, computed max-width was 60%, rendered width 470px of
  800px, before this fix).
  Fixed by adding a `.searchQueryColumnFull` modifier class inside the same media query
  (combined selector `.searchQueryColumn.searchQueryColumnFull` for guaranteed override
  regardless of CSS source order), applied via clsx only when `isConnectOnly`.
  Verified via Playwright viewport resize + getComputedStyle at three widths: 800px
  Connect-only (max-width now 100%, rendered 784.67px of 800px — fixed), 400px
  Connect-only (still 100%, unaffected — the ≤576px rule already handled this case), and
  800px with the dropdown present/homepage's mixed scope (still correctly 60%/470px —
  confirms the fix doesn't leak into cases where the dropdown legitimately exists).
learnings: a JS-level conditional render fix (hiding a sibling column) doesn't
  automatically fix CSS written with `!important` width overrides that assumed that
  sibling's presence — worth checking component stylesheets specifically for hardcoded
  breakpoint widths whenever a conditionally-rendered layout sibling is added or removed,
  not just the grid utility classes.
