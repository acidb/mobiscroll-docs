# Agent Log — 2026-08-04 — algolia — fix Angular template entries missing from search

---
timestamp: 2026-08-04T00:00:00Z
action: fix — search-config.json / search-config-dev.json's text selector was dropping some
  Angular #template-* API entries from the index entirely
context: user noticed agendaEmptyTemplate (Angular) didn't show up in search results at all,
  while its React/JS/jQuery equivalent (renderAgendaEmpty) did. Traced the text selector's
  history: `:not(h3) + p` was added 2024-03-28 (commit 768c4695), well before this session,
  deliberately to skip the bare type-signature paragraph (e.g. "boolean", "() => any") that
  auto-generated options/types/events/methods/renderers always emit as their first paragraph
  after the heading, indexing only the real description below it. Confirmed via .ai/logs/
  2026-07-24.md this same exclusion was already patched once before (adding
  :not(.badge--secondary)) when a version-badge feature inserted a <span> between the heading
  and the type line, breaking the sibling-position assumption the rule depends on - so the
  rule's intent was well-established and deliberate, not a stray leftover.
  The new failure mode found today is different: Angular's #template-* entries (ng-template
  customization props) have no type-signature line at all - the entire real description is the
  first (sometimes only) paragraph after the heading, so the exclusion was wrongly dropping
  real content instead of noise. Verified against the live production HTML (curl-fetched
  mobiscroll.com/docs/angular/eventcalendar/api and .../react/eventcalendar/api): Angular's
  <h3 id="template-agendaEmptyTemplate"> is followed by exactly one <p> with the full
  description merged onto adjacent lines (no blank line = one paragraph, not two), so with no
  li/td fallback in that section, zero Algolia records were ever created for that heading.
  React's <h3 id="renderer-renderAgendaEmpty"> has a separate type-line <p> ("() => any") before
  the description <p>, so it survives.
  Checked every other tracked anchor prefix (opt-, type-, event-, method-, renderer-, view-,
  localization-) against real source files - all consistently have a genuine type-signature
  first paragraph, so the original exclusion is correct for them. Checked slot- (Vue) - its
  first element is a fenced code block (<pre>), not a <p>, so it never matched the exclusion in
  the first place - unaffected. Grepped all frameworks - template- anchors exist only in
  Angular's docs, confirming this is genuinely Angular-specific, not a cross-framework bug.
  Considered and rejected two alternative fixes first: (1) dropping :not(h3) entirely - works
  but reintroduces bare type-signature strings as low-value indexed noise for every option/type/
  event/method/renderer across all frameworks; user judged this too broad/risky as a first move.
  (2) a CSS :has()-based lookahead (skip the first <p> only if a second <p> follows it) - doesn't
  fully solve multi-paragraph template entries (e.g. agendaDayTemplate's first sentence would
  still be dropped) and relies on :has() support in docsearch-scraper's CSS engine
  (cssselect/Scrapy), which wasn't verified and risks silently matching nothing.
outcome: |
  Added one clause to the text selector in both search-config.json and search-config-dev.json:
  `article h3[id^="template-"] + p` - unconditionally indexes the paragraph right after any
  template- heading, since that heading family never has a type line to protect against. Every
  other heading family's behavior is unchanged; this only adds matches, never removes any.
  Verified both files remain valid JSON and structurally identical (besides index_name and a
  pre-existing unrelated whitespace difference in stop_urls). Documented the full text selector
  (both clauses, with rationale and dates) in a new "text selector notes" section in
  algolia-search.md. Not yet run against a real crawl - next production crawl (manual or the
  Monday schedule) will be the first real test.
learnings: |
  When a selector encodes an assumption ("paragraph N is always type X") to solve one real
  problem, the fix for a different but structurally similar problem is often a targeted
  exception keyed to a distinguishing DOM attribute (here, the anchor id's own prefix,
  `h3[id^="template-"]`) rather than a blanket rule change or a lookahead hack - it's exactly as
  safe as the thing it's replacing, provable by grepping real source across every affected
  framework instead of reasoning about the general case in the abstract.
