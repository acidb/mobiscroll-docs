  bare `"default"` docusaurus_tag facet value (not matching either expected
  `docs-default-<version>` or `docs-connect-current` pattern) on ~40% of records, and (2)
  a record with `hierarchy.lvl1: "Server Error"` and null content. Root cause for both,
  found by reading the actual crawl log: `"invalid session id"` Selenium errors — the
  scraper's `js_render: true` setting spins up headless Chrome to render JS before
  scraping, and that browser session crashed mid-crawl on GitHub's hosted runner
  (2 cores/7GB RAM), losing an entire in-flight batch of pages at once (all errors
  timestamped identically) and producing the bogus fallback tag/content on whatever was
  lost. Since Docusaurus is a static site generator — real content and the
  `docusaurus:docusaurus_tag` meta tag are already in the raw server-rendered HTML —
  `js_render` was unnecessary overhead in the first place, not just unstable overhead.

  untouched pending separate verification). User re-ran the Action after committing that
  change themselves and confirmed: crawl succeeded, index updated correctly, no more
  session-crash errors.
learnings: |
  For a Docusaurus (or any SSG) site, `js_render: true` in a docsearch-scraper config is
  usually not needed at all and actively adds a real failure mode (headless-browser
  session crashes under constrained CI runner resources) — worth checking whether a site
  actually needs JS rendering before enabling it, rather than defaulting it on.
  Also: this whole exercise is a good example of why "verified via request-shape
  inspection only, never a real crawl" (flagged repeatedly earlier this week) was a
  real gap and not just caution for its own sake — the first actual crawl immediately
  surfaced two concrete, previously-invisible bugs.
  Next step still open: mirror `js_render: false` into `search-config.json` (prod) only
  after this dev-index result is fully sampled/trusted, and only then consider automating
  the prod crawl on a schedule.

  (type:content) initially looked like a discrepancy (prod: lvl0 "Event Calendar", dev:
  lvl0 "Documentation") but turned out to be comparing two different pages entirely
  (verified via each record's `url` field: .../templating vs .../api) — a false alarm.
outcome: |
  User then ran a more careful, controlled comparison across multiple components
  (eventcalendar, datepicker) and found a consistent, reproducible pattern: dev
  (js_render:false) always falls back to `lvl0: "Documentation"`, while prod
  (js_render:true) always shows the real category name (e.g. "Eventcalendar",
  "Datepicker") for the same kind of page. Confirmed as a genuine, user-visible
  regression via the actual rendered search UI, not just the dashboard: the same result
  ("renderSchedulerEvent") shows breadcrumb `Event Calendar > Scheduler > API` in prod's
  search results vs `Documentation > Scheduler > API` in dev's.
  Root cause theory: the `lvl0` selector
  (`search-config-dev.json`'s xpath targeting `menu__link--active`) depends on a sidebar
  "active" class that is likely only applied client-side after hydration (React comparing
  current route to each sidebar item), not present in the raw server-rendered HTML a
  plain HTTP fetch (`js_render:false`) sees — contradicting the earlier assumption (from
  the previous log entry) that Docusaurus computes this during SSR. `component`,
  `framework`, `docusaurus_tag`, and real page `content` all remain correctly populated
  without JS rendering — only this one field (`lvl0`, used for the search UI's category
  breadcrumb) is affected.
  Decision: do not revert to `js_render:true` (the Selenium crash risk — losing whole
  batches of pages/facets — is worse than a wrong breadcrumb label). Planned fix instead:
  make `lvl0` derive its value from something present in the static HTML (e.g. the page's
  own heading, a statically-rendered breadcrumb, or a formula from the URL's known
  `component` value) rather than a client-only "active" class. Not yet implemented as of
  this entry — investigation of the actual static page source was queued to start on the
  user's signal ("hopplala").
learnings: |
  A theoretical claim about what Docusaurus renders during SSR ("the sidebar active class
  is surely present server-side") turned out to be wrong in practice, a second time this
  same investigation — reinforcing that specific, checkable claims about this site's
  actual rendered output should be verified against real data before being stated as fact,
  not inferred from general framework behavior.
  Also worth remembering methodologically: comparing "record #1 of a filtered facet view"
  between two different indices is not a valid A/B comparison unless the underlying `url`
  field is confirmed identical first — the dashboard's result ordering isn't guaranteed to
  align between separate crawls/indices.

timestamp: 2026-07-24T12:00:00Z
action: found and fixed the real root cause of the lvl0 regression — a broken xpath
  selector, unrelated to js_render — and traced it to the Docusaurus v2-to-v3 migration
context: on user's signal ("hopplala"), investigated the previous entry's open question by
  fetching the live page HTML directly (curl, then a real xpath evaluation via Python
  lxml, since the earlier theory had only been reasoned about, not tested against real
  markup) and checked the other selector levels (lvl1-lvl4) as the user also requested.
outcome: |
  The earlier "client-only active class" theory was wrong. Fetched
  https://mobiscroll.com/docs/react/eventcalendar/templating with curl (three different
  User-Agents tested, including python-requests/Scrapy-style strings, to rule out
  bot-detection serving different markup — all three returned byte-identical HTML), then
  ran the exact `lvl0` xpath from search-config-dev.json against it with lxml.html.
  Structurally, the active sidebar `<a>` (all 3 required classes present, correctly
  nested under `<ul class="...menu__list">`) is genuinely there in the raw static HTML —
  no JS execution needed to produce it. The real bug: the selector ends in
  `/text()[last()]`, which only matches a text node that is a *direct child* of the `<a>`;
  the visible label is wrapped in a nested `<span class="linkLabel_...">`
  (`@docusaurus/theme-classic`'s stock `DocSidebarItem/Link` component — confirmed no
  custom swizzle of it exists in this repo), so `/text()` finds nothing and falls back to
  `default_value: "Documentation"`. This selector bug is completely independent of
  `js_render` — confirmed the raw HTML is identical regardless of rendering method, so a
  fresh crawl of prod's config today would hit the exact same bug. Prod's index only still
  shows correct category labels because it hasn't been re-crawled since before this
  markup changed — stale data masking a live bug, not evidence the config still works.
  Traced the origin via git history: `@docusaurus/core` jumped `2.4.0` -> `3.9.2` in commit
  83330031 ("Update configs and files to v3 format", szily20, 2026-03-20), part of the
  v2-to-v3 migration — Docusaurus v3's theme-classic moved sidebar labels into a CSS
  Modules `<span>`, which the pre-existing lvl0 selector (written for v2's flatter markup)
  was never updated to account for.
  Fix (verified against the real page before applying): changed the selector's
  `/text()[last()]` to `//text()[last()]` (recursive descendant text, not direct-child-only)
  in `search-config-dev.json`, confirmed via lxml to correctly return "Event Calendar".
  Also checked lvl1 (`h1`), lvl2 (`article h2`), lvl3 (`article h3`) per user's request —
  all resolve correctly against the real markup (they use whole-element text content, not
  a fragile direct-child-only text node, so the span-wrapping issue doesn't affect them).
  lvl4 (`article h4`) had zero matches on the sampled page, but only because that specific
  page has no h4 headings — not a selector bug.
  search-config.json (prod) intentionally left unchanged pending a fresh dev-index test
  of this exact fix.
learnings: |
  Confirmed the earlier learning's point a third time: a plausible-sounding claim about
  framework rendering behavior ("the active class must be client-only") was disproven only
  by fetching the real page and testing the real selector against it — reasoning about it
  was not sufficient and would have led to the wrong fix (reverting js_render, discarding
  its real crash-prevention benefit, without fixing the actual bug).
  A crawl config selector can silently break on a framework/theme major-version upgrade
  (here: Docusaurus v2 -> v3, CSS Modules changing sidebar markup) with no build error or
  warning anywhere, and stay undetected indefinitely if the crawl itself is run rarely —
  the bug was live for ~4 months (since the March 2026 migration) before this week's first
  real crawl in a long time surfaced it.

action: answered a security question about storing ALGOLIA_APP_ID/ALGOLIA_ADMIN_API_KEY
  as GitHub Actions repo secrets, given this repo is public
context: user asked whether this is "100% secure," then confirmed the repo is public,
  wanting to understand the actual risk profile before relying on this setup going
  forward.
outcome: |
  No absolute guarantee, but the setup is sound for a public repo, for concrete reasons:
  secrets stay encrypted at rest and are masked in logs regardless of repo visibility;
  `.github/workflows/algolia-crawl-dev.yml` only uses `workflow_dispatch`, which requires
  write/collaborator access to trigger at all — a public visitor can read the workflow
  file (secret *names*, not values) but cannot run it or exfiltrate anything.
  Identified the one real risk that specifically requires public-repo attention: GitHub
  withholds secrets from fork-triggered `pull_request` workflows by default, precisely
  because anyone can fork a public repo and submit a malicious workflow via PR. This
  doesn't apply to the current `workflow_dispatch`-only setup, but is a standing rule for
  any *future* workflow added to this repo: never wire privileged secrets (Algolia admin
  key or otherwise) into anything triggered by `pull_request` (and never
  `pull_request_target`) from forks.
  Also reiterated a residual, non-public-repo-specific point: any collaborator with write
  access can read a secret's live value at runtime (e.g. an echo + transform step evades
  log-masking) — the real trust boundary is the repo's write-access list, not the secret
  mechanism itself. Recommended (not yet done) scoping the Algolia key down from full
  Admin to the minimum ACLs/indices the scraper needs, to reduce blast radius regardless.
learnings: |
  Worth remembering as a standing rule for this repo specifically (public visibility):
  any workflow added here that reads a secret must be gated on workflow_dispatch, push, or
  schedule — never on a fork-triggered pull_request/pull_request_target event. This is the
  one attack surface that actually widens by being public, versus everything else about
  GitHub Actions secrets, which behaves identically in private repos.

timestamp: 2026-07-24T14:00:00Z
action: found and fixed a second, unrelated regression — a version badge breaking the
  `text` content selector, leaking type-signature lines into indexed search content
context: after confirming the lvl0 fix live (breadcrumb now correctly shows
  "Popup > Popup API > Renderers" in both prod and dev), user reported a live search
  result for "renderHeader" showing the snippet "() => any..." in dev instead of the real
  description prod shows, and suspected (based on instinct) something version-related.
outcome: |
  Confirmed via the real page (https://mobiscroll.com/docs/react/popup/api, fetched with
  curl, inspected with lxml/cssselect): every renderer API entry now has a
  `<span class="badge badge--secondary">From: 6.1.0</span>` version badge sitting between
  the `<h3>` heading and the type-signature paragraph (e.g. `<p>() =&gt; any</p>`), a
  markup addition unrelated to this crawl work. The `text` selector's
  `article :not(h3) + p` was written to skip exactly the first paragraph after each
  heading (the type signature) and index only the real description after it — that logic
  depended on the type-signature `<p>` being the heading's immediate next sibling. Since
  the badge `<span>` (not a `<p>`) now sits in between, the type-signature paragraph's
  previous sibling is the badge, not the heading, so the exclusion no longer matches and
  `"() => any"` gets indexed as its own searchable record. The user's "version" instinct
  was directionally right — not `docusaurus_tag`, but these per-entry "From: X.X.X"
  version badges.
  Confirmed this is a crawl-config bug, not a client-app bug — the doc pages and search UI
  are both behaving correctly; Algolia is just faithfully storing bad extraction output.
  Confirmed via grep this affects every framework and every component with renderer
  entries (eventcalendar, datepicker, select, popup), not just this one case — all use the
  identical `badge--secondary` class.
  Fix, verified against the real page before applying (`() => any` disappears from
  matches, the real description remains):
  `"text": "article :not(h3):not(.badge--secondary) + p, article li, article td:last-child"`
  Applied to `search-config-dev.json` only; `search-config.json` (prod) intentionally left
  unchanged pending a fresh dev-index crawl to confirm both fixes together.
learnings: |
  A second, independent confirmation of this week's recurring pattern: a config selector
  written against one version of the site's rendered markup can silently rot the moment an
  unrelated feature (here: version badges on API entries) changes that markup, with no
  error anywhere — only a rare full crawl surfaces it. Worth eventually asking whether a
  more robust `text` selector (not dependent on sibling-position counting at all) would be
  worth the effort, versus continuing to patch this one as markup keeps evolving.
