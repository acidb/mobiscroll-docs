timestamp: 2026-07-30T05:00:00Z
action: fix — retry transient "index does not exist" 404s in algolia/lib.js's browseAll
context: user ran algolia-crawl-dev.yml for the first time since manually deleting
  dev_docs_mobiscroll (to avoid ongoing Algolia costs while this feature was in progress).
  The docsearch-scraper step logged a successful crawl ("Nb hits: 115567"), but the very
  next step (prune-v5-duplicates.js) immediately 404'd on /browse with "Index
  dev_docs_mobiscroll does not exist". User confirmed the index exists now, moments later.
outcome: |
  Root cause: docsearch-scraper crawls into a temporary index and atomically swaps it into
  the real index name at the very end of its run — that swap is an async Algolia operation,
  so the target index can briefly still 404 right after the crawl step reports success,
  before the swap has fully propagated. This isn't a one-off tied to the user having deleted
  the index — the same swap-then-immediately-read race can recur on any future crawl run.
  Fix: algolia/lib.js's browseAll now wraps each /browse call in a new
  withIndexReadyRetry() — retries only the specific, confirmed transient condition (404 +
  "does not exist" in the response body) with a 10s delay, up to 6 retries (~60s budget);
  any other error still fails immediately, since this is deliberately not a
  retry-everything wrapper. algoliaRequest now attaches `status`/`body` to thrown errors so
  the retry condition can be checked without re-parsing the error message string.
  Verified with a mocked-fetch test (not against real Algolia): simulated two consecutive
  404 "does not exist" responses followed by a success on the third call — browseAll
  correctly retried transparently and returned the eventual result; confirmed the retry
  loop terminates on non-matching errors rather than looping forever (structural guarantee
  from the isIndexNotYetVisible guard, not separately re-tested).
learnings: |
  A crawl step reporting success (exit 0, a plausible-looking "Nb hits: N" summary) doesn't
  guarantee the index is immediately readable by a subsequent step when the underlying tool
  does an async atomic swap as its last action — worth checking for this class of race
  whenever a pipeline chains an external tool's "success" directly into an immediate read
  against the same resource.

action: superseded the 404-retry fix above with a stronger freshness gate, after user asked
  a follow-up question that exposed a bigger version of the same race
context: user asked what would happen if Prune/Tag ran against an ALREADY-EXISTING index
  (the prod case) mid-swap, rather than the just-deleted dev index from the incident above.
  Answer: the 404 retry doesn't help there at all — reading an index that already has old
  data succeeds with no error, silently returning stale pre-crawl content, and the
  swap completing afterward would then wipe out whatever Prune/Tag had just done to that
  stale copy. Asked to look for a better solution before implementing, then proceed if one
  is found and safe.
outcome: |
  Considered and rejected: comparing record counts against docsearch-scraper's own logged
  "Nb hits: N" total. Rejected because it requires parsing the tool's stdout (fragile if its
  output format changes) and a >=/=== count check has a real edge case — a re-crawl that
  legitimately produces FEWER records than a stale, larger old count would look "done"
  immediately, before the swap actually happens.
  Implemented instead: a self-planted freshness sentinel. algolia/lib.js gained
  plantFreshnessSentinel() (upserts one throwaway object, objectID
  __pre_crawl_freshness_sentinel__ — also auto-creates the index if it doesn't exist, which
  subsumes the earlier 404 case) and waitForFreshCrawl() (polls the same objectID via a new
  GET-based algoliaGetObject() until it 404s, meaning the swap replaced the whole index and
  the sentinel is gone — proof the fresh crawl is live, independent of record counts or log
  wording). Two new tiny runner scripts (algolia/plant-freshness-sentinel.js,
  algolia/wait-for-fresh-crawl.js) wired into algolia-crawl-dev.yml: Plant now runs right
  before docsearch-scraper (Set up Node moved earlier to support this), Wait runs
  immediately after it and before Prune/Tag. Timeout (12 retries / 10s = ~2min budget) fails
  the job loudly rather than letting Prune/Tag run against stale data.
  Kept the previous entry's withIndexReadyRetry() in browseAll as a cheap defensive
  fallback for unrelated transient network errors — no longer the primary freshness gate,
  but harmless to leave in place.
  Verified with mocked-fetch tests (not against real Algolia): (1) plant -> two
  still-present GETs -> gone on the third resolves cleanly; (2) a sentinel that never
  disappears correctly times out and throws the loud "refusing to run against stale data"
  error rather than silently proceeding.
learnings: |
  When asked "is this safe against case X" and the honest answer is "no, and it's worse
  there because it fails silently instead of loudly," that's a signal the original fix
  addressed a symptom (the specific error message seen) rather than the actual mechanism
  (an async swap racing an immediate read) — worth re-deriving the fix from the mechanism
  once it's questioned, not just patching the one reproduced symptom.

  folds `type:content`/`framework` into the SAME filters string (joined with `AND`) instead
  of splitting them across both parameters; getSearchScope returns an empty facetFilters
  array alongside filters for the v5.35.0 case (never both populated). SearchBar/index.js's
  searchParameters construction now omits `facetFilters` entirely (sets it to `undefined`,

  there). `npm run typecheck` still only shows the pre-existing unrelated HomepageFeatures
  errors.
learnings: |
  Verify library/API constraints instead of asserting them from confidence — I stated
  earlier in this session that facetFilters and filters "combine via implicit AND" in the
  same Algolia query without checking, and that assumption was wrong and shipped as a live

  happened before, not after, calling this done — a good technique to reuse: when two
  similar requests behave differently, diff their actual payloads side by side rather than
  re-reading the code that generated them.

timestamp: 2026-07-30T06:30:00Z
action: replaced the filters-string approach entirely after it hit a second, harder Algolia
  rejection — tagging records directly instead of expressing boolean logic in the query
context: the facetFilters/filters exclusivity fix above didn't fully work — Algolia's actual
  error was "filters: filter (X AND Y) OR Z is not allowed, only (X OR Y) AND Z is allowed".
  The v5.35.0 scope's core expression ("v5.35.0's own records OR (v6 records AND
  presentInV5:true)") is exactly the disallowed (X AND Y) OR Z shape, independent of the
  facetFilters/filters exclusivity issue fixed moments earlier — no amount of `filters`
  string rewriting was going to satisfy both Algolia constraints at once for this logic.
outcome: |
  Root redesign: instead of a boolean `presentInV5` field checked via query-time AND/OR,
  algolia/tag-present-in-v5.js now adds "docs-default-5.35.0" directly onto a shared v6
  record's own `docusaurus_tag` facet, via Algolia's built-in AddUnique array operation
  (`{value: 'docs-default-5.35.0', _operation: 'AddUnique'}` in the partialUpdateObject
  body) — Algolia facets can hold multiple values, and a filter matches if ANY value
  matches, so the record keeps matching its own version's searches (AddUnique only adds,
  never removes docs-default-<currentVersion>) while ALSO matching v5.35.0-scoped searches.
  This collapses the entire v5.35.0 query back to the exact same plain
  `docusaurus_tag:"docs-default-5.35.0"` filter every other page already uses — no boolean
  expression, no filters-string, no facetFilters/filters exclusivity concern, because
  there's no query-time logic left to express.
  Reverted the client-side special-casing this enabled: src/components/Search/util.ts's
  getSearchScope no longer takes a version-scope branch or a currentVersion argument at
  all (getLegacyV5Filters deleted entirely); SearchBar/index.js and SearchPage/index.js
  both dropped their isLegacyV5-conditional filters/facetFilters branches and reverted to
  the single unconditional facetFilters path. isLegacyV5Page/isLegacyV5 and
  rewriteUrlForLegacyV5/transformItemsForLocation are UNCHANGED and still needed — tagging
  the record doesn't change its stored `url` field (still the real v6 URL), so the
  client-side URL rewrite back to `/5.35.0/...` when displaying a v6-sourced hit on a
  v5.35.0 page is still required. presentInV5 boolean kept as a secondary, purely
  informational field for dashboard spot-checks — no longer load-bearing for any query.
  npm run typecheck still only shows the pre-existing unrelated HomepageFeatures errors.
learnings: |
  Two independent Algolia constraints stacked on the same design: `filters`+`facetFilters`
  can't coexist, AND `filters`' own boolean grammar can't express `(A AND B) OR C` at all —
  fixing the first didn't fix the second, since they're unrelated restrictions on the same
  underlying expression. When a query-time boolean expression keeps needing new syntax
  workarounds, that's a signal to look for a way to make the DATA already satisfy a simple
  filter instead of trying to express the logic in the query — tagging the record achieves
  the same result as the OR-of-AND ever could, with zero query-time boolean logic left.
